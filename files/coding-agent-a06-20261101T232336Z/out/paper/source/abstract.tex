Automatic prompt and pipeline optimisers choose a configuration on a benchmark, and the winner's score on those same items is then reported as the system's performance. We ask what that number means and how to report one that means something.
For exhaustive search over $B$ candidates we derive the expected optimism, $\sigma^2(\tau^2+\sigma^2)^{-1/2}\,\mathbb{E}Z_{(B)}$ ($\sigma$: evaluation noise, $\tau$: true spread of the candidates), which grows with the search budget, shrinks with benchmark size and is largest when candidates truly differ least; it matches simulation ($r=\TheoryR$ over \TheoryCells\ settings).
We audit this on a real LLM and benchmark: Qwen2.5-1.5B-Instruct on MMLU-Pro with 72 prompt programs, replaying random search, successive halving, coordinate ascent and a MIPRO-like surrogate search on random benchmarks of 50--800 questions. With $n{=}100$, random search over all 72 reports $\NaiveRSNHund$ points more than the winner's true accuracy, and \FracOptNHund\% of the reported improvement over an average configuration is optimism; a paired test declares the tuned system significantly better than an untuned default in \ClaimNaiveDefNHund\% of benchmark draws although its true gain is \TrueGainNHund\ pt.
Comparing reporting methods by known-truth bias, interval coverage, a no-signal control and false-win rates, we find that hold-out reporting is unbiased but costs precision, cross-fitting under-covers, Ladder and Thresholdout do not repair the bias at these sizes, and a replay bootstrap that re-runs the whole search on resamples removes \BootRemovedMin--\BootRemovedMax\% of the optimism with near-nominal intervals and the lowest error of the generic methods; for exhaustive search, empirical-Bayes shrinkage and a worst-case correction (subtract $\hat\sigma\,\mathbb{E}Z_{(B)}$) are about as accurate on the real pool, but shrinkage fails when a few candidates are much better. A simulator matched to the real pool reproduces the real audit ($r=\MatchedR$). Limits: one small model and benchmark, our own reimplementations of the search families (DSPy was not run end-to-end), and a real pool with little true spread.
