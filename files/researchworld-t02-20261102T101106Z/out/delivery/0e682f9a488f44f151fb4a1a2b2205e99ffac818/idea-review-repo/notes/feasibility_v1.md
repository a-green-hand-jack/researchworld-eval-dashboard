# 可行性评估 v1（idea-review-repo；对象：任务本身与 story-repo 将提出的计划）

依据：`Research objective`、resources.md/data.md/deliverable.md、idea-repo 的 `Brief`，以及我在本沙箱中的**粗测**（脚本 `notes/bench.py`，nn.TransformerEncoder 1 层、4 头、MLP=4d、全批量、AdamW、1 线程；宿主机 load≈85，数字偏悲观且噪声大，只作量级依据）。

## 1. 实测的单步耗时（秒/步，全批量，训练占比 30%）
| p | d_model | 参数量 | s/step |
|---|---|---|---|
| 53 | 32 | 1.6e4 | 0.026 |
| 53 | 128 | 2.1e5 | 0.067 |
| 97 | 32 | 1.9e4 | 0.071 |
| 97 | 128 | 2.2e5 | 0.25 |
| 113 | 64 | 6.5e4 | 0.19 |
（同一配置在不同时刻差 2–3 倍，说明受宿主机争用影响。）

## 2. 成本量级（规划估计，非测量）
- Nanda 主线配置（p=113, d=128, 4e4 步）：约 0.25–0.4 s/步 ⇒ **单次 3–4.5 CPU 小时**。25 个这样的运行 ≈ 80–110 CPU 小时，超出「数十 CPU 小时」，且本沙箱/作业只有 2 CPU。⇒ **不可行作为全网格**；只能作为 1–3 个锚点运行。
- p≈53–61、d∈{16…128}：0.03–0.1 s/步，4e4 步 ≈ 20–70 CPU 分钟/次。5 个宽度 × 5 种子 ≈ 25 次 ≈ 10–20 CPU 小时。**可行**。
- 总预算建议：主实验 ≤ ~25 CPU 小时，其余（第二条件、消融、机理诊断）≤ ~15 CPU 小时，留 ≥30% 余量给重跑。2 个 CPU 并行下约 20–30 小时墙钟，但宿主机争用可能放大到 2–3 倍。

## 3. 真正的约束不是 CPU，而是世界预算
- 世界总模型时间 7200 s（硬上限 10800 s）、96 个 turn，由 8 个位置共享（≈每位置 900 s、≈12 turn）。任务书的「一周」不是约束；**写代码、改代码、评审往返的次数**才是。计算作业本身不耗模型时间，但作业在 `ht-resource run` 之外不能跑，且作业若输出不变且几乎不占 CPU 会被判空闲结束（需周期性 flush 进度行）。
- 因此：实验代码应**一次写好、先小规模验证、再全量启动**；全量运行必须**可断点续跑、按配置/种子落盘**，使失败不重跑全部；分析脚本与作图脚本应能直接读落盘结果。避免「看结果再加新网格」的多轮迭代；预留的追加运行要预先列好（预算内的 B 计划）。

## 4. 科学上的风险与应有的边界
1. **规模的操作化与混杂**：宽度改变时 lr/wd/初始化/步数预算若固定，则「规模效应」与「有效正则强度/有效学习率」不可分。必须至少两个明确区分的条件：(A) 超参固定；(B) 每个规模各自做小范围调优或按预先写明的规则缩放。只做 A 的结论只能写成「在这些固定超参下」。
2. **右删失**：小模型可能永不泛化（容量不足/权重衰减过强），大模型可能无延迟（t_val≈t_train）。须预先登记步数预算 T_max，删失运行按生存分析或报告删失比例处理，不得丢弃；T_max 需据 pilot 定，否则「不泛化」与「还没泛化」无法区分。
3. **容量下限**：d 过小（如 d≤16）可能连训练集都记不住，延迟泛化无定义；网格应覆盖「记得住」的最小规模，并把「训练都拟合不了」作为单独结果报告。
4. **延迟的度量对阈值与评估频率敏感**：评估间隔应远小于 t_train（对数间隔或每 50–100 步）；阈值预先登记；对 99% vs 100% 做敏感性检查。
5. **种子数**：延迟在同一配置内跨种子方差很大（量级可达数倍）。每配置至少 5 个种子，且数据划分与初始化种子分开记录；3 个种子的置信区间对「趋势」基本无力。要宣称单调趋势，需 ≥5 个规模点 × ≥5 种子，或改为秩相关/回归斜率并给 bootstrap CI。
6. **p 与运算的外推**：只有 p≈53–113、模加法时，结论适用范围只能写这一范围。加第二个运算（如模乘/减）或第二个 p 作为**小规模稳健性检查**是可行的（每项 ≤ 10 CPU 小时），但不要把全网格复制到每个 p。
7. **可证伪性**：假设要写明被反驳的观察（例如：「t_val 随宽度单调下降」被反驳 = 秩相关的 95% CI 包含 0 或符号相反）。「视条件而定」的结论也要有预先写明的条件边界。
8. **机理诊断**（权重范数、restricted/excluded loss、Fourier Gini）只对少数运行做（存检查点代价小，但分析代码量大）；不要为每个运行都做，除非解释本身依赖它。
9. **禁止访问的论文**：不要用以「model size / scale + grokking」为核心的检索词；相关工作写作请只用起步文献与无关文献，偶遇即停并记录（idea-repo 的 Brief 已写）。

## 5. 加速与降本手段（可行，建议采用）
- 手写 1 层 Transformer（或把多个种子堆叠为 batch 维用 bmm/vmap 同时训练），避免 nn.TransformerEncoder 的开销；小 d 时 CPU 受调用开销支配，堆叠种子能显著提速（未实测，需 pilot 验证）。
- 评估只在对数间隔步做；训练达到「val ≥99% 且连续保持 k 次评估」后提前停止（即时判定泛化），未达则到 T_max 作为删失。
- 每个作业 1–2 线程，2 个作业并行；检查点与结果 JSON 增量写入。
- 使用小 p（53–67）做网格，p=113 只做 Nanda 锚点（1–3 个运行）以对齐文献并作结果合理性检验。

## 6. 建议 story-repo 采纳的范围（可行性边界）
- 必做：pilot（3–4 个宽度 × 1–2 种子，确定 T_max、lr、wd、评估间隔，≤2 CPU 小时）→ 主网格（≥5 个宽度 × ≥5 种子，条件 A）→ 条件 B（同宽度子集，≥3 种子）→ 删失感知的统计分析。
- 可选（按剩余预算）：训练集占比交叉、第二个运算/p 的稳健性、少数机理诊断。
- 不做：全网格在 p=113 上复制；深度扫描（除非作为 ≤3 点的小消融）；GPU 方案。
- 判据：若 pilot 显示所选网格在 T_max 内多数运行被删失，应缩小 p 或提高 lr/wd 组合，而非无限延长 T_max。

## 7. 待 pilot 证实的不确定项（本评估无法凭空给出）
- 各宽度下 t_train 与 t_val 的实际量级，决定 T_max（我的估计 4e4 步来自 Nanda 配置，未对更小 p/d 验证）。
- 种子堆叠的实际加速比。
- 宿主机争用下的真实吞吐（单次测量 2–3 倍波动）。
