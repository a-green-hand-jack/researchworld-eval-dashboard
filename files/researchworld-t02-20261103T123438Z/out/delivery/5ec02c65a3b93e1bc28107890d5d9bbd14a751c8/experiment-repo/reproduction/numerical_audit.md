# Terminal metric replay and independent precision audit

The registered algorithm trains/evaluates in float32 with an indexed concatenated-one-hot forward pass. Stored curves and thresholds refer to that implementation. Audits never substitute a float64 outcome into those curves.

The original independent dense-float32 terminal audit used fixed1e-5 absolute/relative loss tolerance. It passed84 primary/frozen runs, then failed on decay_w512_b01 held-out loss at the96-input control checkpoint. Exact indexed float32 replay matched the stored loss. For all8 completed decay0.1 width512 runs, an alternative dense-float32 expression differed by up to0.001953125 in logits and3.0041e-5 in held-out loss, with identical predictions; maximum logits were16173–20282. These are measured diagnostics, not training failures or grounds to discard a seed. The failed tooling timing/trace is preserved in reproduction/derived-timing/partial96-initial-failed.json. Raw runs/trainer remain unchanged.

The corrected audit keeps the original strict loss/count comparison for exact replay of the actual indexed float32 implementation. Separately it evaluates the mathematical dense one-hot network in float64 and checks every logit against a standard scale-aware forward-roundoff envelope. For unit roundoff u=2^-24 and gamma(n)=nu/(1-nu), the input affine addition has error at most gamma(2)*(sum of absolute selected weights + absolute bias). ReLU is exact and1-Lipschitz, so this propagates directly to hidden errors E. The output bound is

`E @ abs(Wout).T + gamma(2width+1)*((abs(h64)+E) @ abs(Wout).T + abs(bout))`.

The2width+1 envelope allows separate multiply/add rounding rather than assuming fused accumulation. Float64 reference arithmetic has much smaller roundoff; a1e-10 logit floor covers the observed scale and is explicit. This bound assumes the registered ReLU networks and ordinary finite IEEE arithmetic, not arbitrary activations, overflow/underflow or future recipes. All registered inputs/weights/results are finite and audited. A different activation is refused until a corresponding error analysis is supplied. Terminal losses and exact counts are replayed, rather than relaxing their fixed tolerances to pass a different arithmetic expression.

Float64 predictions may differ on close decisions. Every actual disagreement is recorded, with its ordered-pair ID, subset, float32/float64 metric and logit-error diagnostics; the audit requires that it lie within the propagated ambiguity envelope. A float64 top-two margin greater than twice the maximum class error certifies agreement; a differing certified prediction fails. Certification is conservative, and an uncertified point need not actually change. These diagnostics expose arithmetic sensitivity instead of requiring impossible bitwise equivalence across matrix-multiplication formulations or hiding near ties. None certifies exact real arithmetic at all training updates: only initial identity and saved terminal state are independently available. Event sensitivity remains computed from the original measured float32 curves.
